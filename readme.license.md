## 0. 一句话结论

**代码你几乎可以任意改；自由必须原样传下去；网络服务必须交源码；名字和 Logo 不在许可范围内。**

AGPL-3.0 是"强 copyleft + 网络条款"许可。它对**修改行为本身几乎零限制**，全部约束集中在
**分发（conveying）** 与 **网络交互（§13）** 两个触发点。只要你不分发、不对外提供服务，
你可以把这个项目改到面目全非而无需任何动作。

## 2. AGPL-3.0 授予你的四项自由

许可的正面授权集中在 §2（Basic Permissions）与 §4–§6（Conveying）：

1. **运行自由** — 不受限制地运行本程序，用途不受审查（§2 明确：运行未修改程序的行为不受限制）。
2. **研究与修改自由** — 获取源码、研究其运作、以任何方式修改，用于任何目的。
3. **再分发自由** — 逐字复制并分发副本（§4），可收取介质费与技术支持费。
4. **分发修改版的自由** — 分发你的修改版（§5/§6），使他人也获得同样的四项自由。

**关键理解**：copyleft 不限制你"改什么"，而限制你"分发时能不能收窄下游的自由"。
答案是不能——这是 AGPL 的全部机制。

## 3. 硬约束逐条对照

### §4 — 分发逐字副本

分发未修改的源码时必须：
- 在每份副本上**显著且恰当地**保留版权声明；
- 保留所有声明"本代码依 AGPL 发布"以及 §7 追加条款的文字；
- 保留所有无担保声明（§15/§16）；
- 随副本提供 AGPL 全文。

### §5 — 分发修改后的源码版本

在满足 §4 的基础上，**四项追加义务**：

| 条款 | 义务 | 本仓落实位置 |
|---|---|---|
| §5(a) | 显著声明"你修改了本作品"并给出**相关日期** | `NOTICE`（Modified by SantaChains / 2026） |
| §5(b) | 显著声明本作品依 AGPL 及 §7 追加条款发布 | `LICENSE` + `NOTICE` + `README` License 段 |
| §5(c) | 把**整体**作品按 AGPL 授权给任何取得副本的人 | 未新增任何限制性条款 |
| §5(d) | 若有**交互式用户界面**，必须显示 Appropriate Legal Notices | 见下方「§5(d) 落地要求」 |

> **§5(d) 落地要求**：桌面 App、Web SPA、CLI 的"关于"或启动信息中，应可见：
> ① 版权归属（原作者 zerx-lab + 改版者 SantaChains）；② 无担保声明；
> ③ 本程序依 AGPL-3.0 授权；④ **如何获取对应源码**（fork 仓库 URL）。
> 本 fork 已在 `README` / `NOTICE` 承载文本，**若你重构了关于页，务必保留这四项**。

### §6 — 分发非源码形式（二进制、安装包、容器镜像）

分发编译产物时，**必须**以 §6(a)–(e) 之一提供"对应源码"（Corresponding Source）：
包含全部源文件、构建脚本、接口定义文件，以及控制编译与安装所需的脚本。

实践建议（本项目适用）：
- **GitHub Release 同址提供源码 tarball**（§6(a)/(b) 组合），最省事；
- 容器镜像（`ghcr.io/SantaChains/fluxdown-server`）**必须**在镜像说明或仓库中给出源码位置；
- 不要采用"书面承诺三年供源"（§6(b)）——运维成本高且易失效。

> **注意**：对应源码必须与该二进制**版本一致**。发 tag 时同步推源码，不要只发 exe。

### §7 — 追加条款：能加什么、不能加什么

你**可以**追加的（且仅限这七类，§7(a)–(g)）：免责与责任限制、要求保留合理法律声明或作者归属、
要求修改版标记为不同以免混淆来源、限制以宣传为目的使用许可人姓名、
**拒绝授予商标法下的使用权**、要求赔偿担保。

你**不可以**追加任何其他限制——任何超出 §7 列举范围的条款，接收者可直接移除（§7 末段）。

### §8 — 违约即终止

违反许可（最常见：分发二进制不给源码、部署服务不给源码），**许可自动终止**。
首次违规在被通知后 30 天内改正可自动恢复；重复违规需版权人明确恢复。
这意味着违规状态下你连"使用"的权利都失去了。

### §10 — 不得施加进一步限制

向下游传递时不得附加任何限制其行使 AGPL 权利的条款。
**"仅限个人使用""不得用于商业""不得转发"这类附加条款一律无效且构成违约。**

### §13 — 远程网络交互（AGPL 的核心特色，本项目高风险条款）

> 若你修改了本程序，并让用户**通过计算机网络远程与之交互**，你必须为这些用户
> 提供一个**免费获取对应源码**的机会。

本项目**天然踩在这一条上**，因为它内置：
- `fluxdown_server`（headless 服务器，编译期内嵌 Web SPA）
- REST / aria2 JSON-RPC / MCP API
- Web 管理界面

**判定边界**：
| 部署形态 | 是否触发 §13 |
|---|---|
| 本机自用桌面 App，无对外端口 | ❌ 不触发 |
| 仅 `127.0.0.1` 监听，仅自己访问 | ❌ 不触发（无"其他用户"） |
| 局域网内供家人/同事访问 Web UI | ✅ **触发** |
| 公网部署、NAS 服务、给客户用 | ✅ **触发** |
| 提供 SaaS 形式的下载服务 | ✅ **触发** |

**满足方式**：在 Web UI 显著位置（页脚、关于页、登录页）放一条指向
`https://github.com/SantaChains/FluxDown` 的源码链接即可。成本极低，遗漏则违约。

> **这是 AGPL 与 GPL 的唯一实质差异**，也是选择 AGPL 的项目最常被追责的点。
> 若你 fork 后重构了 Web 前端，**页脚源码链接不得删除**。

### §11 / §15 / §16

- §11：贡献者授予专利许可，但仅限其自身持有的相关专利；
- §15/§16：无担保、责任限制。分发时**必须原样保留**，这也是保护你自己的条款。

## 5. 不由版权许可授予的权利（独立边界）

这一节最容易被忽略：**AGPL 是版权许可，它不处理商标、域名、服务资产与人格权。**

### 5.1 商标与品牌名（§7e）

- AGPL **明确允许**许可人拒绝授予商标法下的权利（§7e）。
- 因此 **"FluxDown" 名称、原 Logo 图形、视觉标识** 是否可继续使用，
  取决于 zerx-lab 是否注册/主张商标权，**与代码许可无关**。
- 现状风险评估：本 fork 继续使用 "FluxDown" 名称与基于原 SVG 的图标。
  这在开源 fork 实践中很常见（Linux 发行版重打包惯例），但**法律上不是零风险**。

**降风险的三级选项**（按风险从高到低）：

| 方案 | 做法 | 风险 | 成本 |
|---|---|---|---|
| A. 现状 | 保留 "FluxDown" 名 + 原生 Logo，仅加 fork 声明 | 中 | 零 |
| B. 限定式命名 | 改为 "FluxDown (SantaChains Build)" 或 "FluxDown-SC" | 低 | 低 |
| C. 完全改名换标 | 独立名称 + 全新 Logo，仅在 NOTICE 说明基于 FluxDown | 极低 | 中（需重跑图标管线） |

> 若日后收到原作者关于名称/标识的异议，**方案 C 是彻底解法**：
> `bun scripts/gen_icons.ts` 以 `assets/logo/fluxdown_logo.svg` 为唯一源，
> 换源 SVG 后一条命令即可重生成全平台 50 个图标文件。改名的工程成本因此很低。

### 5.2 域名与服务资产

以下**不属于**版权许可标的，一律不得占用、冒用或继续调用：
- `fluxdown.zerx.dev`（原官网域名）；
- 原 FluxCloud 云服务端点、账号体系、计费与推荐码系统；
- 原作者的 API key、签名密钥、更新源、遥测端点；
- 原作者的插件市场索引仓、主题仓的写入权限。

> 这正是本 fork **整体移除云账号功能改为纯本地**的合规动因之一：
> 继续调用原作者的云端点既无授权，也会把用户数据发往第三方。

### 5.3 人格权与背书

不得以任何方式暗示原作者为本 fork 提供支持、认可或背书（§7d 的镜像义务）。
"Based on FluxDown by zerx-lab" 是**陈述来源**，合规；
"由 zerx-lab 推荐 / 官方认证" 则构成虚假背书，不合规。

> 建议在"关于/开源许可"页面内置第三方许可清单（可用 `cargo about` 自动生成）。

### 6.2 外部受管组件：已有的合规隔离，不得破坏

`native/engine/src/components/mod.rs` 的模块注释明确标注了**合规边界**：

> 组件是宿主侧受控的外部可执行程序，**不随安装包分发**，
> 运行时按需由用户在设置「组件」页主动触发下载。

这是刻意的许可隔离设计：

| 组件 | 典型许可 | 若捆绑分发的后果 |
|---|---|---|
| **ffmpeg** | LGPL-2.1+ 或 **GPL-2.0+**（取决于构建开关，如 `--enable-gpl`、libx264） | GPL 构建捆绑进 AGPL 分发包会引入额外的 GPL 传染面与源码提供义务 |
| **yt-dlp** | Unlicense | 本身宽松，但捆绑会带来版本追踪与站点合规责任 |

**禁改红线**：
1. **不得**把 ffmpeg / yt-dlp 二进制打进安装包、Docker 镜像或 Release 资产；
2. **不得**改成"首次启动自动静默下载"——必须保留用户主动触发的交互；
3. 若确需捆绑 ffmpeg，**只能**使用明确的 LGPL 构建（无 `--enable-gpl`），
   并履行 LGPL 的可替换性义务（动态链接 + 提供替换手段）。

## 7. 分发场景决策矩阵

| 场景 | 必须公开源码 | 必须显示源码链接 | 可否收费 | 备注 |
|---|---|---|---|---|
| 本机自用，不分发 | ❌ | ❌ | — | 完全自由，改成什么样都行 |
| 改完只推自己的私有仓（无他人访问） | ❌ | ❌ | — | 未发生 conveying |
| 发 GitHub 公开仓（源码） | ✅ 本身即源码 | ✅ README | ✅ | 履行 §4/§5 |
| 发 Release 二进制 / 安装包 | ✅ 同址提供 | ✅ 关于页 | ✅ | §6，版本须对应 |
| 发 Docker 镜像 | ✅ | ✅ 镜像说明 + Web UI | ✅ | §6 + §13 双触发 |
| 内网部署 headless server 供他人用 | ✅ | ✅ Web UI 页脚 | ✅ | **§13 触发** |
| 公网 SaaS 下载服务 | ✅ | ✅ 显著位置 | ✅ | **§13 触发，最高风险** |
| 企业内定制版，仅内部员工使用 Web UI | ✅ 对这些员工 | ✅ | ✅ | 员工即"远程用户" |
| 卖预装了本软件的硬件（NAS 盒子） | ✅ 随机提供 | ✅ | ✅ | §6，需给购买者源码 |

> **可以收费**是 AGPL 常被误解的点：许可**不禁止商业化**。
> 你可以卖二进制、卖服务、卖支持、卖硬件。唯一要求是**买家同样获得四项自由**。
> 你不能做的是"卖闭源授权"或"付费解锁 = 不给源码"。

## 8. 常见误区订正

| 误区 | 事实 |
|---|---|
| "AGPL 禁止商业使用" | 错。可自由商用、可收费，只是不能闭源 |
| "改动超过 30% 就算原创，可自己定许可" | 错。衍生作品无"改动比例"豁免，AGPL 覆盖整体 |
| "只要不改源码，直接部署就没义务" | 错。§13 对**修改版**要求给源码；未修改版部署时 GPL 系仍建议给出，AGPL §13 针对 modified version，但本 fork **已是修改版**，义务成立 |
| "内网不算对外服务" | 错。只要有**其他用户**通过网络交互，§13 即触发 |
| "只发二进制不发源码，别人问了再给" | 高风险。§6(b) 的书面承诺路径义务更重，实践上应同址发源码 |
| "把 AGPL 换成 MIT 更自由" | 无权这么做。你不是版权人，不能降级许可 |
| "删掉原作者名字就看不出是 fork" | 违约（§4/§5），且 git 历史与代码指纹可证 |
| "加一句'仅供学习交流，禁止商用'更保险" | 反而违约。§10 禁止施加进一步限制 |
| "依赖里有 Apache-2.0，会不会冲突" | 不冲突。Apache-2.0 与 AGPL-3.0 单向兼容（可被 AGPL 吸收） |
| "Logo 是代码的一部分，随许可一起给我了" | 错。商标权独立，§7e 明确可保留 |

## 9. 发布前自查清单

每次打 tag 发布前逐项确认：

- [ ] `NOTICE` 存在，含原作者归属、改版者、修改年份、fork 源码 URL；

## 10. 出现争议时的应对顺序

1. **保留证据**：完整 git 历史、`NOTICE`、发布记录，证明归属声明始终在位；
2. **30 天窗口**：AGPL §8 给首次违规者 30 天自动补救期，收到通知后立即修正并书面回复；
3. **区分性质**：若争议关于**代码许可**，按 §4–§6/§13 补齐义务即可；
   若关于**商标/名称**，则与许可无关，走 §5.1 的方案 B/C 改名换标；
4. **不要沉默**：AGPL 的自动终止条款使沉默期同时丧失使用权，成本远高于修正成本。
