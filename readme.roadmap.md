## 1. 尚未实现的下载相关技术

### 1.1 传输协议 / 标准

| 技术 | 状态 | 价值 | 成本 |
|---|---|---|---|
| **HTTP/3 (QUIC)** | ❌ 未实现 [已核实] | 弱网/移动无 HOL 阻塞 + 连接迁移 | 高（需 rustls 迁移） |
| **SFTP / FTPS / WebDAV** | ❌ 未实现 [已核实：无 `sftp/ssh/webdav/ftps` 命中] | 企业/NAS/私有云场景 | 中（依赖 `ssh2`/`dav` crate） |
| **metalink 多镜像聚合** | ❌ 未实现 [已核实：无 `metalink/multi_source` 下载源聚合] | 多源并发 + 自动校验（aria2 强项） | 中 |
| **MPTCP（多路径 TCP）** | ❌ 未实现 [推断] | Wi-Fi+蜂窝bonding 韧性 | 中（内核/平台依赖） |
| **WebTransport / WebSocket 下载** | ❌ 未实现 [推断] | 新型 CDN 流、抗封锁 | 中 |
| **Tor / 匿名网络下载** | ❌ 未实现 [推断] | 审查规避、隐私 | 低-中（SOCKS 已具备，加路由即可） |
| **IPFS / WebTorrent（WebRTC P2P）** | ❌ 未实现 [推断] | 去中心化分发、浏览器内 peer | 中-高 |

### 1.2 校验与完整性

| 技术 | 状态 | 说明 |
|---|---|---|
| **HTTP 层端到端 checksum 校验** | ❌ 未实现 [已核实：engine 层仅 BT 有 piece hash，无 HTTP 下载的 hash 校验路径] | 用户给定 SHA-256/MD5 时未做 end-to-end 验证；文件损坏只能靠 Range 重下，无主动校验 |
| **修复式下载（从备用源补全坏块）** | ❌ 未实现 [推断] | 单源损坏时需整段重下，无跨源块级修复 |
| BT 分片校验 | ✅ 已实现 | 见 §0 |

> 注意：上述"HTTP 校验"为 engine 层结论；若 Flutter UI 另有"下载完成后校验"开关请二次核实，本处不主张其存在。

### 1.3 多源 / 协同加速

| 技术 | 状态 | 说明 |
|------|---|---|
| **同源多镜像（metalink 式）** | ❌ 未实现 | 同一文件多 URL 并发拼合 |
| **跨协议聚合（同一 hash 的 HTTP↔BT 互备）** | ❌ 未实现 [推断] | 源挂掉时自动切换协议续传 |
| **自建 P2P 加速（迅雷式基础设施）** | ❌ 未实现 | 见 `readme.frontier.md` §3.2：靠自建离线下载 companion 实现，非逆向 |
| **LAN P2P 缓存共享** | ⚠️ 部分（有 `local_pairing` 设备下发，但无缓存复用）[已核实] | 可扩展为局域网内同文件块级共享 |

### 1.4 其他（低优先级 / 无意义）

- **Usenet/NNTP**：专业小众，价值低。
- **Gopher**：已淘汰，无意义。
- **传统 FTP 主动模式 / TFTP**：场景极少。

## 2. 下载速度的硬件与网络底层边界（探索"天花板"）

> 核心命题：**软件最多只能逼近物理链路天花板；分段解除的是"服务端单连接限速"与"单连接窗口"限制，BBR 解除的是"弱网丢包/缓冲膨胀"限制。磁盘/NIC/CPU 是物理天花板，通常 ≤1 Gbps 下不构成瓶颈。**

### 2.1 物理带宽天花板（不可逾越）

- **ISP 套餐速率 = 硬上限**。离线下载也"不能突破用户物理带宽上限"（迅雷官方亦承认）。任何优化只能让你**更逼近**这个上限，而非超越。

### 2.2 单连接吞吐公式（分段为何有效）

```
单连接吞吐 ≤ min(CWND, RWND) / RTT
```
- 一条 TCP 连接的吞吐受**拥塞窗口(CWND) ÷ 往返时延(RTT)** 约束。
- **分段 = 开 N 条独立连接**，每条各有自己的窗口 → 总吞吐 ≈ N × 单连接上限，直到撞上 ISP 天花板或服务器单 IP 总限速。
- 这正是 IDM/FluxDown 快于浏览器的根本原因。

### 2.3 带宽-时延积 BDP（高 BDP 链路的隐藏陷阱）

```
BDP = 带宽 × RTT
```
- 1 Gbps 链路、RTT 20 ms → BDP = 2.5 MB。CWND 必须 ≥ 2.5 MB 才能喂满链路。
- **长肥管道**（卫星 RTT 600 ms、跨国专线）：BDP 可达数百 MB，旧栈未开窗口缩放会严重欠利用。
- 老内核需 `tcp_window_scaling=1`；现代系统默认开。

### 2.4 服务端单连接限速（分段的主战场）

- 大量源站对**单 IP / 单连接**限速（如 200 KB/s）。分段把 1 个被限速的连接拆成 16 个，总带宽 ×16。
- **风险**：过多段触发服务端 429/503 → FluxDown 的 AIMD 已能回滚（见 `readme.gap.md` §3.1）。

### 2.5 缓冲膨胀 Bufferbloat（弱网的隐形杀手）

- 丢包驱动型 CUBIC **填满路由器队列**直到丢包 → RTT 从 20 ms 暴涨到 400 ms，吞吐反而掉。
- **BBR** 模型驱动、保持队列空 → 消除此问题（见 `readme.frontier.md` §2.1，弱网 +45%~+120%）。

### 2.6 磁盘 I/O 边界

| 链路 | 速率 | 磁盘需求 | 结论 |
|---|---|---|---|
| 1 Gbps | 125 MB/s | SATA SSD 500 MB/s 富余 | 不绑定 |
| 2.5 Gbps | 312 MB/s | SATA SSD 临界 | 接近 |
| 10 Gbps | 1250 MB/s | 需 NVMe（3-7 GB/s） | **绑定 SSD** |

- FluxDown 已用**定位写（seek_write）+ 稀疏标记**，避免顺序写碎片；HDD 上并发段写重叠区会有 seek 抖动，SSD 无此问题。
- 极端多段并发 + HDD → 随机写放大，此时**减少段数反而更快**（与 AIMD 目标一致）。

### 2.7 CPU / TLS 边界

- 多 Gbps 下，**单核 TLS 解密**会成为瓶颈（AES-NI 缓解但非无限）。
- 异步 I/O + 零拷贝（splice/IO_uring）可降 CPU；Rust+tokio 架构已友好。
- 分段越多，调度/校验 CPU 开销越大 → 存在**边际递减点**，AIMD 的软试探预算正是为此设的。

### 2.8 NIC / 端口 / 内核参数

- **NIC 速率 = 硬天花板**（1G/2.5G/10G）。多连接再多也超不过网卡。
- **ephemeral ports 耗尽**：上千连接需调 `net.ipv4.ip_local_port_range` + `tcp_tw_reuse=1`。
- **窗口缩放 / 时间戳**：长肥管道必需。

### 2.9 丢包与 goodput（有效吞吐）

- 丢包链路 goodput 随丢包率平方下降；**FEC 前向纠错**可补但引入冗余开销，价值随场景权衡。
- BBR 容忍 ~2% 随机丢包不崩（loss-based 算法在此已瘫）。

### 2.10 MTU / 巨帧（LAN 内）

- 9000 字节巨帧减少包头占比，LAN 内大文件传输略增有效吞吐；跨公网无用（中间设备不支持）。

### 2.11 边界总图

```
[ISP 套餐] ──硬上限──┐
[NIC 速率] ──硬上限──┤
[磁盘 I/O] ──物理───┤
[CPU/TLS] ──物理───├──→ 软件可逼近，不可超越
[单连接窗口÷RTT] ──分段解除──┤
[服务端单连接限速] ──分段解除──┤
[缓冲膨胀/弱网丢包] ──BBR解除──┘
```

## 3. 可以继续探索的功能设计（路线图，按性价比排序）

### 3.1 协议补完（确定性收益）
- **[P1] HTTP 层 checksum 校验 + 坏块修复**：给定 hash 时端到端验证，损坏块从同文件备用镜像/跨协议重取。低成本高信任增益。
- **[P1] metalink / 多镜像聚合**：引入 metalink 解析 + 多源拼合，直接追平 aria2 的核心差异点。
- **[P2] SFTP / WebDAV / FTPS**：面向企业/NAS/私有云，依赖 `ssh2`/`dav` crate。
- **[P3] IPFS / WebTorrent**：去中心化分发，生态未成熟，谨慎。

### 3.2 智能加速（已在前两文档展开）
- **[P0] per-host 并发画像持久化**（重启不归零）。
- **[P1] 自建离线下载 companion**（aria2 + yt-dlp + 自有服务器）。
- **[P1] LAN P2P 缓存共享**：基于已有 `local_pairing`，扩展为局域网块级复用 → 家庭/办公室多设备秒传同名文件。
- **[P2] 跨协议聚合**：同一 hash 的 HTTP↔BT 互备续传。

### 3.3 网络层
- **[P1] 启用 BBR**（OS 级或经 QUIC 顺带）。
- **[P3] QUIC/HTTP3**（TLS 后端迁移后）。
- **[前瞻] MPTCP / WebTransport**。

### 3.4 体验与可观测性（高用户感知）
- **[P1] 全局速度调度器**（跨下载聚合限速，追平 aria2 global limit）。
- **[P1] 实时瓶颈分解可视化**：区分"源限速 / 网络 / 磁盘"三段瓶颈，界面显示当前绑定约束——把 §2 的边界模型做成用户可感知的诊断。
- **[P2] 带宽 QoS 预留**：为其他应用保留带宽。

### 3.5 韧性
- **[P2] Tor / 代理链匿名下载**（SOCKS 已具备，加路由层）。
- **[P2] 跨协议断点续传**：源失效自动切换协议。
- **[P3] 智能退避/重试**：基于历史成功率的源排序。

## 4. 边界探索实验建议（如何实测你的天花板）

| 实验 | 方法 | 验证的边界 |
|---|---|---|
| 裸链路速率 | `iperf3 -c <server>` | ISP/NIC 硬上限（§2.1/2.7） |
| 分段收益 | 单连接 vs 8/16 连接拉同一文件 | 单连接窗口限制（§2.2/2.4） |
| BBR vs CUBIC | `tc netem` 注入延迟+丢包，对比两种 CC | 缓冲膨胀/弱网（§2.5） |
| 磁盘绑定 | `fio` 顺序写压测对照下载速率 | 磁盘 I/O 边界（§2.6） |
| 连接数上限 | 渐进增加段数至报错，观察端口/文件描述符 | 内核参数边界（§2.8） |
| 跨协议续传 | 制造 HTTP 源 503 看是否自动切 BT | 韧性设计（§3.2/3.5） |

## 5. 一句话总结

FluxDown 的**协议广度已超 aria2、代理能力已是卖点**，真正的空白是**协议补完（SFTP/WebDAV/metalink）、HTTP 端到端校验、跨源/跨协议协同**三处——都是"做加法"而非"重写"。速度的物理天花板由 ISP/NIC/磁盘/CPU 决定，**软件只能逼近不能超越**；分段解除的是服务端单连接限速与单连接窗口限制，BBR 解除的是弱网缓冲膨胀——这两笔"免费增益"目前都还没吃满。**最该优先探索的功能设计**是：① P0 per-host 画像持久化、② P1 HTTP checksum+坏块修复、③ P1 metalink 多镜像、④ P1 BBR 启用、⑤ P1 全局限速 + 瓶颈可视化。其余（QUIC、自建 P2P、MPTCP）按 `readme.frontier.md` 的条件触发推进即可。
